# GitHub Follow-up and Automation

Applies only to `bot_loop` mode. The SKILL.md Draft PR Mode gate takes precedence: draft runs skip all sections here, and a ready-to-draft change ends remaining external follow-up/waits after any necessary internal tandem/push completes.

Read when the first ready-PR tandem cycle completes; reuse thereafter. Apply the portable runtime snapshot/delta rules to avoid interpreting unchanged feedback.

## Review Thread Follow-up

Use retained reviewer conclusions and fixer records, never independently reinterpret findings in the orchestrator.

1. Use runtime `snapshot` to fetch all PR review threads with pagination, original author, complete comments and resolution state. Read changed entries and unresolved evaluated finding references from saved paths; retain full evidence on disk. Match evaluated findings by recorded thread/comment IDs and URLs across every pass in the cycle. For findings without a review thread, retain their outcome; do not invent a destination or substitute a PR summary comment.
2. Before replying, reconcile saved follow-up records and existing replies. Complete Out-of-Scope Tracking Issues below for eligible findings, including findings without a thread or with an already resolved thread. Skip unchanged outcomes already posted, including after a retry. A changed outcome or newly recorded tracking issue may justify a new reply.
3. Reply individually to each evaluated unresolved thread with the reviewer's explicit no-change reason, or a pushed fix that the reviewer verified plus relevant validation. For a valid out-of-scope finding, explain why it is non-blocking for this PR and link its verified tracking issue; describe it as deferred, never fixed or invalid. Keep pending findings unresolved; do not post a success claim for them. Link every referenced commit SHA to its GitHub commit URL.

   Use plain-text replies by default. Apply a supplied profile's tag protocol only when explicitly applicable, including any requirement to refresh tags before re-requests.

4. Resolve an addressed selected-reviewer bot thread only after its reply succeeds and its finding is verified fixed by a pushed commit, explicitly needs no change, or is explicitly non-blocking for this PR and deferred to a verified tracking issue. Do not automatically resolve other reviewers' threads.
5. Verify reply and resolution results and append their IDs/URLs and outcomes with runtime `record`, using separate intent/result attempt IDs. On uncertain API results, refetch before retrying to avoid duplicate replies. Report failures without claiming follow-up succeeded.

Invocation authorizes these thread replies and resolution of addressed selected-reviewer bot threads.

## Out-of-Scope Tracking Issues

Create or reuse a GitHub issue before replying only for valid, important external findings the reviewer explicitly verifies are wholly unrelated to the PR and non-blocking under [External Change Requests](../../bork-review/SKILL.md#external-change-requests), even if the original review called them blocking. A change request with even slight concrete relevance must be fixed in this PR instead; do not create or reuse a tracking issue as a substitute. Require the reviewer's recorded evidence of no connection before issue lookup or creation, and return ambiguous or related deferrals to the reviewer. Exclude rejected findings, nits, style preferences and optional suggestions without a substantive problem. Issue creation does not satisfy an in-scope blocker or qualify a bot for re-review.

1. Before creating an issue, reconcile retained finding-to-issue mappings, source-thread replies and existing issues in the recorded base repository. Search both open and closed issues using the finding's behavior, affected code and source links; inspect plausible matches to determine whether they cover the same underlying problem even when their titles differ. Reuse a matching open issue and link it in each applicable thread. Inspect a matching closed issue's resolution; create a new issue only if the problem remains and that resolution does not cover it. Group findings only when one issue actually covers the same problem.
2. Only after confirming no existing issue covers the finding, create it in the recorded base repository using `gh issue create --repo <owner/repo> --title <title> --body-file <path>`. Include the concrete problem, impact, available reproduction/evidence and affected code, why it is outside this PR's scope, suggested fix or acceptance criteria, and links to the PR and original review comments/threads. Preserve reviewer attribution and distinguish verified facts from suggested investigation. Do not invent evidence or apply unrelated labels, assignments or milestones.
3. Save separate intent/result attempts with runtime `record`, mapping stable finding IDs and source comment/thread URLs to the issue repository, number and URL. Verify the issue exists and covers the finding before posting its link. On an uncertain creation result, reconcile GitHub issues before retrying; never blindly create a duplicate. Retain mappings across passes, cycles and resumed runs, and include issue links in the durable final result.
4. After verifying newly created issues, complete PR Body Issue Log below before replying to their threads. Reused issues do not require a new creation entry; issues created earlier in this run with an incomplete body update still do.
5. If issue creation, lookup, verification or the required PR body update fails, leave the affected thread unresolved, record follow-up as incomplete and report the operational blocker. Resume this phase without repeating completed issues, body entries, replies or pushes. Do not claim the finding is tracked until the issue is verified.

Invocation authorizes these tracking issues in `bot_loop` mode. Refresh draft state before creating issues and apply the Draft PR Mode gate if it changes.

### PR Body Issue Log

For each issue created by this workflow, append one timestamped entry under `## Review follow-up issues` in the PR body. Create the section at the end if absent. Use the issue's GitHub `createdAt` timestamp in UTC, its linked number and title, and a brief scope reason, for example: `- 2026-09-17 08:30:00 UTC: Created [#123](https://github.com/OWNER/REPO/issues/123), Handle expired tokens. Deferred as outside this PR's scope.` Do not use closing keywords such as `Fixes` or `Closes` for deferred issues.

Fetch the current body and draft state immediately before editing. Preserve all existing content, modifying only this section to append missing entries. Deduplicate by issue URL in the section and retain original timestamps on retries. Batch pending entries into one update using `gh api -X PATCH repos/<base-owner>/<repo>/pulls/<number> -F body=@<path>`, because `gh pr edit --body-file` fails on some orgs with a projects-classic deprecation error. Only append: never rewrite the body or drop `Closes #N`, which silently stops the issue auto-closing. If a sentence in the original summary became factually untrue, correct only that sentence. If the body changed since it was read, rebuild from the latest body before writing.

When a cycle pushed fixes, append the same update one `## Review round N` section (create it per cycle, never edit earlier rounds) with `- Fixed: <finding>, <what changed, file:line>`, `- Declined: <finding>, <reason>` and `- Downstream: <repositories checked, result>` lines. It backstops findings raised only in a review body, which have no thread to tag, and gives humans the history.

Record the intended entries and update result separately with runtime `record`, then refetch to verify all entries and preservation of existing content. Reconcile uncertain results before retrying. A failure leaves this phase incomplete even if issue creation succeeded. Invocation authorizes these PR body updates in `bot_loop` mode; apply Draft PR Mode before writing.

## Re-request Bot Reviews

Always complete and verify Review Thread Follow-up for the entire cycle before manually re-requesting any review, including through native actions, bot commands, retries, or resumed runs. Every evaluated unresolved thread requiring a reply must have its current outcome posted successfully; an existing verified reply for an unchanged outcome satisfies this requirement. Check retained reply evidence before each request. If any required reply is missing, failed, or uncertain, finish or reconcile it first and block all re-requests until follow-up is verified complete. Never request reviews in parallel with pending replies. A review that starts automatically after a push does not waive this gate for manual requests.

Apply any supplied profile's request budget and final-review prerequisites in addition to the gates below.

Re-request a bot review when the completed cycle has either re-review trigger: new code was successfully pushed, or a new verified tracking issue was created from a valid blocking or important review finding because changes were requested. Both triggers in one cycle require only one fresh request per eligible bot. Run only while the PR is still ready. Refresh `isDraft` immediately before each request; if draft, record remaining external phases as `skipped_draft` and return to owner cleanup under Draft PR Mode:

1. Discover bots from previous PR reviews/comments and review automation.
2. For a `code_pushed` trigger, qualify each discovered bot that previously reviewed the PR so it can evaluate the new code. For a `review_issue_created` trigger, qualify the bot whose blocking or important finding is referenced by the new issue, using retained finding, comment or thread provenance. Human findings, another bot's findings, rejected findings, nits, optional suggestions and no-change conclusions do not qualify a bot through the issue trigger. Merge the qualifying sets when both triggers occurred.
3. Record one fixed wait scope for the combined trigger: the current PR HEAD, new issue URLs and source review provenance, required PR checks, and review runs from qualifying bots. Unrelated optional checks and nonqualifying bot activity do not enter that scope. If a nonqualifying bot supplies a required check, wait for the check as a merge requirement without re-requesting that bot.
4. For each qualifying bot, detect an automatic review started for this combined trigger. Require evidence associating the activity with the current HEAD and, for a same-SHA issue-only trigger, evidence that it started after the issue and related PR follow-up were completed. Timing alone is insufficient when the target is ambiguous.
5. If it did not start automatically, use a native re-request action or a command evidenced by repository configuration/documentation or the bot's own PR message. Never guess commands. Follow any supplied profile's applicable re-request path before the generic direct request and removal below. Order the cycle as push, confirm the PR `headRefOid` equals the pushed SHA, thread replies, body update, then the request; a request after a failed push wastes a round. For a bot reviewer that already approved, a plain `gh pr edit --add-reviewer` may not start a run: remove it first (`gh api -X DELETE repos/<owner>/<repo>/pulls/<number>/requested_reviewers -f 'reviewers[]=<bot>'`), then add it back. If the bot is already in the requested reviewers or its run already started for this SHA, do not touch it. Request each qualifying bot at most once per trigger fingerprint, composed of the current HEAD and sorted new issue URLs, saving evidence before and after the request. Reconcile uncertain results before retrying.
6. Record each bot as skipped, automatically started, requested, or qualified but blocked. If a qualifying bot cannot be safely requested or its request target cannot be established, report an operational blocker instead of silently treating it as reviewed.

## After a Bot Approval

An approval still ships threads, often a dozen. Fix and resolve them within the same cycle without requesting another bot round, subject to the existing one-manual-request limit. Then be precise: if any commit landed after the approved `commit_id`, record and report that the approval sits on the pre-fix commit rather than implying head is approved. Never imply head is approved from a stale approval.

## Wait for GitHub Review Automation

1. Save the current review target SHA, new issue URLs, source review provenance, required check identities, qualifying bots and initial activity as an immutable runtime automation scope. Read `automation-poll` and `automation-assess` schemas in [runtime actions](../../bork-review/references/runtime-actions.md). Determine required checks from GitHub PR/rules metadata. If that metadata is inaccessible, report a blocker rather than silently changing the wait scope.
2. Use `automation-poll` every 30 seconds, refreshing PR HEAD and `isDraft` alongside scoped activity. Assess only changed evidence with `automation-assess`; unchanged polls reuse saved assessments and advance quiet time mechanically. If it becomes draft, stop waiting, record `skipped_draft`, and return to owner cleanup; do not wait for pending runs or start another feedback cycle. Refresh scoped runs for the same SHA, including reruns or successors of scoped checks. Ignore unrelated bot activity when deciding whether the wait is complete or the quiet period should restart.
3. Treat an expected required check that has not reported for this SHA as pending, not successful. Wait while any scoped check or qualifying review run is queued or in progress. Successful, failed, neutral, skipped, and cancelled runs are terminal. A failed check is feedback for the next reviewer, not an instruction for the orchestrator to fix code or stop the review loop.
3a. Each poll, read the bot's own check runs on the head commit (`gh api repos/<owner>/<repo>/commits/<head-sha>/check-runs --jq '.check_runs | map({name, status, conclusion})'`). Queued or in progress means keep waiting. Completed with a failure or cancellation and no review result means the bot will not answer: stop and report. Nothing ever started means suspect the re-request never registered, not a slow bot. Always report which of these states was seen, so it is clear whether you are waiting on the bot or the bot is broken.
4. Where a qualifying bot provides an explicit completion signal, require it for the current review target SHA and trigger fingerprint. Do not time out known pending work. An access failure or ambiguous run identity is an operational blocker.
5. Where a qualifying bot has no explicit completion signal, require terminal scoped checks/runs and two minutes of unchanged qualifying-bot comments/reviews. Reset this quiet period only for activity in scope. With no qualifying bots, use terminal required checks plus two minutes of quiet measured only against those checks.
6. Save completion evidence and start the next review cycle. The reviewer refreshes all relevant PR feedback then, including any unrelated bot feedback that arrived, without chasing it in this wait phase.
