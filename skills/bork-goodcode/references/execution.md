# Review and Fix Worker Execution

For standalone goodcode, select the first usable driver: **hc, Herdr, tmux, Screen, native**. Resolve capabilities before creating the worktree and persist `execution_driver`, capability evidence, reasons higher-priority drivers were unavailable, and the verified CLI/shell profile in `session.json`. In doitall, inherit the approved batch driver instead of independently changing it. Resume an existing run with its recorded driver; reconcile and report unavailable capabilities rather than silently switching a live run. For legacy sessions without a saved driver, establish the original driver from retained agent/process records; preserve native execution when those records establish the old native workflow, and block if identity is ambiguous.

Use the OS-independent discovery rules in [agent execution](../../bork-doitall/references/panes.md). Invoke installed version/help commands through structured argument arrays and inspect the current execution environment. Do not require Unix discovery tools, Unix filesystem paths or Bash, and do not exclude a driver by OS name. Paths and executables must belong to the same environment; do not silently bridge to WSL, MSYS or another machine. Confirm the destination shell separately from the OS and use its supported command quoting.

Use the shared `environment.php` membership helper before assessing driver usability. When the user reports being inside hc, Herdr, tmux or Screen, pass the matching `expected_environment` value. Missing variables in a sandbox or detached backend are unresolved caller context, not evidence that the terminal driver is unavailable. Follow the shared execution-boundary checks, including unique frontend recovery and context-aware terminal commands. Block unresolved reported membership before considering a lower-priority driver.

- **Herdr:** require the inherited managed-pane context and reachable compatible API in [Herdr execution](../../bork-doitall/references/herdr.md), the invoking host's CLI, supported shell quoting and two concurrent worker panes. No native child-agent delegation is required for these terminal workers.
- **Tmux:** require a usable tmux interface, the invoking host's CLI, supported destination shell and two concurrent worker sessions. Probe the installed tmux version/help and configuration read-only, even on Windows. Installation alone does not establish compatibility. Do not start sessions to probe availability.
- **Screen:** require verified membership, GNU Screen query/control support, local procfs window identity verification, the same host CLI and two concurrent worker sessions under the [Screen contract](../../bork-doitall/references/screen.md).
- **Native:** require the invoking host's documented native delegation interface to run review and fix concurrently, with at least three simultaneous slots including goodcode and one delegation level at this depth. No terminal CLI or multiplexer is required.

Report a blocker if none can run both workers. Selection never changes the required models, reasoning effort, permissions or host. Resolve model and resume controls from the installed provider's help/catalog; a terminal launch must explicitly preserve the selected role/model/effort binding. Do not use default CLI models when they differ from those bindings.

For `hc`, follow the shared [hc contract](../../bork-doitall/references/hc.md). Its interactive workers remain available after a turn; require matching durable acknowledgment and result before reuse, and verified final process shutdown before cleanup. This supersedes the exit-after-turn runner convention below only for hc.

## Launch and Monitor

In all modes, goodcode owns one review worker and one fix worker, launched concurrently against the same temporary worktree and coordination records. A terminal worker is a separate CLI process, not a new goodcode owner. Require it to load its named skill, receive `orchestrated` mode and the exact runtime brief path, acknowledge completion and exit when its cycle turn finishes. Give it only the compact role brief and durable records. Retain the normal `.status` handoffs, write ownership, completion acknowledgments and loop guards.

For native mode, use the host's documented launch/resume/wait interface. Save returned provider agent/session IDs immediately.

For terminal modes, prepare one immutable job and launch JSON per role and attempt using the [terminal launcher contract](../../bork-doitall/references/panes.md). Each has `role: review` or `fix`, `cwd` set to the dedicated worktree, the verified CLI argument array, actual `shell`, and a unique `exit_record`. Save intent before launch and returned terminal IDs before submission where applicable. Herdr uses the shared runner through the [Herdr pane contract](../../bork-doitall/references/herdr.md). Tmux uses `php <doitall-skill>/scripts/tmux.php launch <absolute-launch-json>`; choose distinct sessions such as `gc-<pr-number>-review-<run-suffix>` and `gc-<pr-number>-fix-<run-suffix>`, reconciling collisions before launch. Do not call batch scheduling or phase transition actions for these workers; goodcode already owns their lifecycle.

Persist driver, terminal session/pane IDs, provider session IDs, role/model bindings, job/exit paths, brief/acknowledgment paths and worktree identity in per-role session records. If either launch is uncertain, inspect it before retrying; never duplicate a role. If one worker fails to start, safely stop and reconcile its peer, preserving all diagnostics. Keep normal authentication and terminal input; surface questions and permission prompts immediately, with exact prompt and the driver's navigation command. In doitall, relay these to the master/coordinator.

Poll both workers and their durable records with foreground waits of at most 60 seconds. Herdr idle/done status, a dead tmux pane, an exit code or a final message alone never proves a successful turn. Require matching completion acknowledgments, reviewed HEAD and expected coordination state. Verify both CLI processes and any descendants stopped before advancing the cycle, publishing completion or removing the worktree.

## Reuse and Cleanup

Apply [worker session reuse](../../bork-review/references/reuse.md). Distinguish provider session IDs from terminal pane IDs: a live shell pane does not mean its previous worker is still running. For a documented provider resume, use a new immutable job/exit record and fresh cycle brief, preserving the role/model identity. If provider resume is unavailable, start a fresh CLI from compact durable records after reconciling the old worker. Never replay uncertain fixes, commits or acknowledgments.

Capture each stopped terminal worker's output and exit evidence before closing only its owned pane/session. Herdr cleanup uses the recorded pane ID and preserves the user's surrounding workspace/session. Tmux cleanup uses the recorded owned pane, including failed outcomes. Retain durable diagnostics, provider session IDs and role bindings for later cycles. A missing or live worker blocks cleanup until reconciled. Standalone goodcode retains its existing publication authorization; driver selection creates no extra permission to answer prompts or change external state.

For Screen workers, use `screen.php launch` with distinct review/fix session names and immutable jobs. Persist the exact `session`, `pane`, optional `socket_dir`, configuration, job and exit paths. Inspect, interrupt, capture and close through the [Screen lifecycle contract](../../bork-doitall/references/screen.md). Resume the provider through a fresh session/job only after the old worker and descendants stop; never resurrect a zombie window or replay a job.
