# BORK Prify

Apply the shared [profile contract](../bork-doitall/references/profile.md) before starting. Preserve any supplied profile in nested calls; default to `generic`.

## Goal and Input

Turn exactly one GitHub issue into a validated draft PR, implementing entirely in a dedicated temporary git worktree. Remove the worktree only after verifying publication and safe cleanup.

Accept a plain issue number, `#123`, or a GitHub issue URL. Resolve numbers against the current checkout's GitHub repository. For URLs, verify the issue repository matches the checkout's project, accounting for a verified upstream/fork relationship; never infer a relationship from matching repository names. If the project is ambiguous, mismatched, or the directory is not a Git checkout with a GitHub remote, report the missing context before creating a worktree.

## Portable Execution

Read [the shared portable runtime](../bork-review/references/portable-runtime.md) once. Use its helpers for local discovery, locks, atomic records, worktree creation, commit verification and cleanup checks. Cache the resolved issue/base/head identity and execution brief in this run; resume from phase evidence without repeating completed discovery or validation. Refresh changing remote state at publication and cleanup boundaries as required below. This skill needs no agent delegation.

## Explicit Doitall Inputs

When invoked by doitall, read [extra instruction routing](../bork-doitall/references/instruction-routing.md), load the brief's `instruction_paths` before acting, and apply its scoped requirements alongside issue intent. Include instruction dispositions in the durable result.

A `bork-doitall` task may supply an explicit `implementation_repository`, `base_override` (repository, branch, verified SHA, parent PR URL), `commit_email` resolved from applicable user/repository instructions, falling back to local Git author configuration, and a durable result path. When `implementation_repository` is supplied, require the current checkout and its remotes to verify that exact repository and allow the issue's request repository to differ; retain the issue repository for reading requirements and closing references. Validate and honor the implementation repository and base before worktree creation and PR publication; do not silently substitute the issue repository or default branch. A stale, missing, ambiguous, or incompatible implementation/base repository blocks the target. Run as one native child of the target master in either batch driver mode. Do not delegate or take over promotion, goodcode or merge decisions. Pass any interactive blocker to the master with the exact prompt. Before exiting, atomically write `phase: prify`, `status: complete`, `pr_url`, `published_head`, `cleanup_success: true`, the issue and implementation repositories, base/head identities, validation summary and `validation_path`, records path and cleanup outcome to the supplied result path. Write `status: blocked` with blocker evidence on failure. These explicit inputs supplement the single-issue contract; ordinary invocations retain their defaults.

## Resolve Context and Acquire Ownership

1. Use runtime `inspect` once to record the original repository root, branch, HEAD, and worktree state. Confirm `gh` authentication. Read applicable local instructions before setup. Preserve the original checkout's files, index, branch, and unpublished commits throughout the run.
2. Resolve the explicit GitHub host, base repository, and writable head repository from the doitall `implementation_repository` when supplied, otherwise from the issue target, and verify them against the current checkout's remotes. Use `gh repo view` with explicit repository context and inspect remote fetch/push URLs. Do not assume `origin` is the upstream or push destination. For fork workflows, verify the relationship and available permission to push a generated branch; do not create a fork automatically.
3. Read the issue title, body, comments, labels, state, and URL with explicit repository context. Resolve relevant linked requirements without recursively following unrelated links. Inspect issue timeline/relationships with pagination for open linked PRs, and inspect any retained run's head branch for an existing PR. A body-only issue read is insufficient to establish that no PR exists. Stop for a closed issue, an unrelated existing implementation PR, or missing required product context. A matching PR from this run is handled through recovery.
4. Select the intended base branch now, following explicit user/issue/repository requirements and otherwise the default branch. Verify it exists in the base repository. Fetch that branch and record its resolved commit SHA. Use this same branch for implementation and PR creation. If requirements later change the intended base, stop publication until the work is reconciled and validated against the newly selected base.
5. Resolve an absolute persistent records root using `git rev-parse --path-format=absolute --git-common-dir`, then `<common-git-dir>/bork-prify/<host>/<base-owner>/<base-repo>/issue-<number>`. Acquire a per-issue lock through exclusive directory creation before creating a worktree or branch. A lock coordinates runs sharing this Git repository; it does not lock GitHub or other clones, so publication still requires remote rechecks.
6. Inspect any existing lock, active-run pointer, and session. Resume an identified inactive run only after verifying the previous agent has stopped. Never remove an ambiguous/live lock, overwrite a run, or create a second worktree for it. For a new run, create a unique run directory and record its active pointer and owner.

## Persistent Run Records and Recovery

Keep `session.json` and validation/publication records under the persistent run directory, outside the worktree and its disposable Git metadata. Never commit these files. Publish each update through a temporary file in the same directory followed by atomic rename; retain earlier phase evidence.

Record run ID, lifecycle owner, issue URL, original checkout, worktree path, generated branch, host, base/head repositories, exact fetch/push destinations, selected base branch/SHA, implementation HEADs, owned support paths, validation results, publication attempts, remote HEAD, PR URL, and cleanup state. Save planned branch/worktree paths before creation and mutation intent before a push or PR request; save verified results afterward.

On restart, reconcile the recorded phase with Git worktree metadata, local commits, remote branch HEAD, and PRs for the exact head repository/branch. Resume the first incomplete phase, not a fresh implementation. After an uncertain push or PR response, query remote state before retrying. If a matching draft PR already exists, verify its base, head repository/branch, and commit before proceeding to cleanup. Do not create a duplicate PR. A closed, merged, non-draft, or mismatched PR is a blocker requiring reconciliation, not permission to create another automatically.

If a recorded worktree is missing, ownership is unclear, or local/remote mutations cannot be attributed safely, preserve evidence and report the blocker. A cleanup-pending run resumes cleanup only after rechecking publication. Mark a blocked run discoverably and release its lock only after this agent's work has stopped; retain the active pointer for recovery. Retain completed run history after successful cleanup.

## Prepare the Worktree

1. Choose a branch named `<type>/<issue-number>-<short-slug>`, using a Conventional Commits type appropriate to the issue. Check both local refs and the exact head repository for collisions; add a unique suffix when needed. Never reuse or reset an unrelated branch. Confirm the remote lookup succeeded rather than treating an access failure as absence.
2. Record the intended branch and unique path under `/tmp`, such as `/tmp/bork-prify-<repo>-<issue-number>-<suffix>`. Create it with runtime `worktree-create` using the recorded branch, path and base SHA. Do not use force flags. Record successful creation immediately.
3. Read applicable repository instructions inside the new worktree before installing dependencies or changing files. All implementation, staging, commits, and validation happen there. Use explicit issue/PR repository context for GitHub commands from this point onward.
4. Inspect the original checkout for needed ignored/untracked dependencies, fixtures, caches, test databases, and local configuration. For missing support paths, link only paths that the planned commands will read without modifying. Copy or recreate mutable support files, dependencies installers may rewrite, and anything requiring edits. When read-only behavior is uncertain, use an independent copy or installation. Never symlink editable source or let tests write through a shared database/configuration into the original environment.
5. Record created support paths and whether each is a link, copy, or disposable generated artifact. Keep local-only support paths out of staging. Recheck status after setup. Intended tracked fixture/config changes must be independently editable files and belong to the issue's diff.

## Implement, Validate, and Commit

1. Implement only the issue's requirements using project patterns and instructions. Do not stash, reset, stage, commit, or copy unpublished source changes from the original checkout.
   Before validating, apply [quality checks](../bork-review/references/quality-checks.md): search for the defect pattern at other call sites, run the pre-push sweep over the diff, and for a bug fix add a test that fails with the fix reverted when the project has a suite. Keep the change small: the AI code review scorer adds points at 6+ meaningful files or 500+ changed lines (lock files, `vendor/`, `dist/` and minified files excluded), so split work that sprawls across unrelated concerns and report the seams instead of publishing one oversized PR.
2. Run the narrowest meaningful tests/checks and required repository validation, using the project's declared commands (`composer.json`, `package.json`, `Makefile`, CI workflow) on touched files only. Save a durable `validation.json` with commands, outcomes, coverage, full log paths and content/configuration/environment evidence under [validation handoff](../bork-review/references/reuse.md). Include `validation_path` in the result so goodcode can independently decide which checks remain reusable. Resolve failures before publication; do not claim success when required validation cannot run.
3. Inspect the full diff and staged diff. Stage only intended issue changes, excluding support links, local configuration, generated artifacts, and run records unless a tracked change is explicitly required by the issue.
4. Create signed Conventional Commits using the existing signing setup and the explicit doitall `commit_email` when supplied, otherwise resolve the email from applicable user/repository instructions, falling back to local Git `user.email`; block if no identity is available. Keep titles concise, bodies at most five factual bullets, and omit co-authorship. Use runtime `verify-commits` for new commits only; retain its per-SHA result and separately verify commit scope. Confirm the final committed tree matches what was validated; changes after validation require the relevant checks again.

## Publish Exactly One Draft PR

1. Recheck the issue is open, selected base branch still exists, and no competing open linked PR appeared. Query PRs for this exact head repository/branch as well. Resume a verified matching PR from this run; stop for a competing PR. If the selected base tip changed, inspect its impact and reconcile/revalidate when necessary before publishing. Never silently switch bases.
2. Confirm the generated remote branch is absent before its first push, or exactly at this run's last verified remote SHA during recovery. Unexpected remote movement is a blocker. Invocation authorizes pushing only this generated branch to the recorded head repository. Push using an explicit destination, `git push <head-remote-or-url> HEAD:refs/heads/<generated-branch>`. Never force-push, overwrite an unrelated branch, or push the original checkout's branch. Remote checks are best-effort concurrency protection; after any uncertain result, reconcile before proceeding.
3. Verify the remote branch SHA equals the intended committed HEAD and persist that result. Refresh linked/head PR checks immediately before creation. If a competitor appeared after the push, preserve the published branch and report the blocker instead of creating another PR.
3a. Choose the PR title and labels before creation. Use `<type>(<scope>): <summary>` with the type from the branch type and a scope naming the area changed. Add only labels that exist in the base repository and match its conventions. Apply any supplied profile's additional metadata rules without understating the change or manipulating review scope.
3b. Before creating the PR, verify any assignee or reviewer you will set has access (`gh api repos/<owner>/<repo>/collaborators/<login> --silent`) and any label exists, since a failed create is awkward to recover. Never drop a chosen label to make the create succeed.
4. Create the draft with explicit base repository, base branch, and head identity, using `gh pr create --draft --repo <base-repository> --base <selected-base> --head <branch-or-owner:branch> --title <title> [--label <label>]...`. Resolve a supported head identity for fork PRs; if CLI support is insufficient, use an authenticated GitHub API with the same explicit identities. Do not guess a destination.
5. Follow the implementation repository's PR template when present. Describe the concrete change and validation, link the issue, and use `Closes #<number>` when the issue and PR share a repository or `Closes <owner>/<repo>#<number>` when they differ and automatic closure is appropriate. Write multiline content to a file and pass `--body-file`. Check the resulting PR exists, is open and draft, has the chosen title and labels, targets the selected base repository/branch, and uses the recorded head repository/branch and expected commit SHA. Persist its URL and verification results. A URL alone is insufficient proof of correct publication.
6. GitHub registers `Closes` as a closing link, and shows the PR on the issue and its project board, only when the PR targets the default branch of the issue's repository. When the PR's `closingIssuesReferences` (GraphQL) lacks the issue, as with a stacked or non-default base, link it explicitly: resolve the issue and PR node IDs and call the `addCloseIssueReferences` mutation with `issueId` and `pullRequestIds`. The call is idempotent; skip it when the link already exists. Re-read `closingIssuesReferences` to confirm the issue is listed and record the outcome in the durable result. A failed link does not block the draft; report it. Keep `Closes` in the body so the issue still closes on merge to the default branch.

## Cleanup and Reporting

- Keep the worktree if publication failed, required verification is incomplete, source changes are uncommitted, or any implementation commit is unpushed. Preserve its branch and retained records on blockers.
- After verified publication, inspect tracked, untracked, and ignored files. Remove only recorded disposable support paths/artifacts and never follow support symlinks into their targets. If unexpected or unowned untracked/ignored content, or uncommitted tracked changes, remain, keep the worktree, mark cleanup pending, and report their paths; do not invoke worktree removal. Git may delete ignored files even without force, so a clean tracked status alone is insufficient. Preserve unexpected or user-created files. Do not use force removal or blanket clean commands to make deletion succeed.
- Return to the original repository root and run `git worktree remove <recorded-worktree-path>`. Verify removal before marking cleanup complete. Do not run broad worktree pruning; reconcile only this run's metadata if removal reports a problem. Keep cleanup-pending state if removal fails.
- Leave the generated local and remote branches intact. Do not merge the PR, delete its remote branch, or manually close the issue. Do not advance or reset the original checkout after publication.
- Retain the per-issue lock through cleanup. Once removal succeeds, mark the session complete, clear only this run's active pointer, and release its lock. Keep run history for later inspection.
- Save PR and issue URLs, branch, selected base, validation/manifest path, retained records and cleanup outcome in the durable result. Print the [TLDR report](../bork-review/references/reporting.md); if blocked, show the exact blocker and next recovery action.
