# BORK Doitall

Apply the shared [profile contract](../bork-doitall/references/profile.md) before starting. Preserve any supplied profile in nested calls; default to `generic`.

## Contract

Accept any number of distinct issue/PR root targets from the current GitHub project, supplied as numbers or URLs. A root target is one canonical issue or PR, not one raw argument. Recursively discover GitHub sub-issues beneath supplied issues, include every descendant in read-only triage, and add each open actionable descendant to the work queue. A target's request repository and implementation repository may differ when explicit requirements or verified relationships establish where the code change belongs. Process one target's implementation and review at a time by default before starting the next eligible target. In approved `DOMERGE` batches, finalize merges after implementation in reverse dependency order. Allow two or three concurrent implementation targets only when explicitly requested by the user. Select hc when actively inside hc, otherwise Herdr when actively inside Herdr, otherwise tmux when actively inside tmux, otherwise Screen when actively inside Screen, otherwise native; verify membership separately from capacity and block invalid explicit context without falling back. Use one hc master terminal, Herdr master pane, tmux or Screen master session, or native master subagent per active target under the capability checks in [agent execution](references/panes.md). Each master delegates prify and goodcode as native subagents; goodcode runs review and fix through the selected execution driver. Keep all agents on the invoking host. Goodcode chooses models and reasoning effort from a per-PR effort tier within that host's available capabilities.

Read [scheduling and ownership](references/scheduling.md), [agent execution](references/panes.md), [durable batch runtime](references/batch-runtime.md), and [review profile](references/profile.md) once in the caller/coordinator before launching masters. Each target master reads [target workflow](references/target-workflow.md) and the batch runtime. Reuse sibling skills and their portable records rather than rediscovering context or duplicating implementation rules.

Only an explicit `go` response to the displayed execution plan authorizes creating and pushing the generated/fix branches through the sibling skills, marking owned draft PRs ready, and their documented ready-PR review follow-up. Accept `REVIEWER=xxx` with any nonempty value, preserving the supplied reviewer exactly. Default to `REVIEWER=NONE`; the exact value `NONE` and the standalone, case-sensitive `NOREVIEWER` token are equivalent. They skip external review requests, the promotion review gate, and ready goodcode, including its review/fix cycles, bot re-requests and ready-PR follow-up; draft goodcode and ready promotion still run. Any other value requests that reviewer and enables the review gate and ready goodcode. Never default to a reviewer other than `NONE`. Resolve conflicting reviewer options before the plan approval gate. Accept `PROFILE=generic` or `PROFILE=<absolute-profile-file>` per [review profile](references/profile.md); a profile never relaxes the `go`, `REVIEWER` or `DOMERGE` gates. Accept `EFFORT=low`, `EFFORT=standard` or `EFFORT=high` to set every target's starting effort tier; without it goodcode computes the tier per PR under [effort tiers](../bork-goodcode/references/effort-tiers.md). Any other value is an error to resolve before the plan approval gate. Merge only when the invocation includes the separate, case-sensitive token `DOMERGE` and the approved plan explicitly includes merging. Both tokens may be used together; the merge gate then uses the applicable completed phases and current GitHub protection checks. Neither token replaces the separate `go` gate. Without `DOMERGE`, never merge. Never automatically retarget existing PRs, delete remote branches, add work targets other than verified sub-issue descendants of supplied roots, or bypass CLI permissions. This target-scope limit does not prohibit tracking issues created by the approved ready-PR follow-up in `bork-goodcode`; those issues are not added to this batch. PR ownership is the authenticated GitHub account for its host, not a hardcoded username or Git author email.

## Coordinator

For new visible-layout batches, read [shared layout and acceptance status](references/layout.md). Preflight the existing coordinator area before the preview, include any blocked visual acceptance explicitly, and create the approved tree once after `go`. Pass the journal and stable concurrency slot to each master and goodcode owner. Keep previously approved runs on their recorded launch contract.


Before normalizing targets or launching workers, read [extra instruction routing](references/instruction-routing.md). Preserve appended user instructions, resolve their target/role scope, and carry them through every relevant sibling-skill handoff, cycle and resume.

1. Detect the invoking host and verify authentication, Git, Node.js 22+, and sibling skills. Select the execution driver under [agent execution](references/panes.md): use the shared environment helper to verify active membership, passing `expected_environment` when the user reports hc, Herdr, tmux or Screen, select hc over Herdr over tmux over Screen over native, then validate only the selected driver against the documented CLI, nesting and capacity requirements. Reconcile missing caller context across sandbox or detached-backend boundaries before declaring a reported terminal environment inactive. Resolve supported prompt/model/reasoning controls once. If membership is unverifiable or the selected driver cannot run the workflow, report the concrete blocker; never switch agents or use Fable as a fallback. Do not choose a host merely because its executable is installed.
2. Using read-only discovery, canonicalize inputs, deduplicate root aliases without imposing a root-target limit, verify ownership, recursively enumerate sub-issues, resolve each request repository and implementation repository, and triage every root and descendant under the scheduling reference. Keep all supplied roots and verified descendants in the same execution batch unless the user explicitly requests separate batches. When more than one distinct canonical root remains, load [bork-batch](../bork-batch/SKILL.md) and apply its embedded planning mode in the coordinator, reusing this discovery context. Skip grouping for a single canonical root, even when it has descendants. Ask for missing decisions when sub-issue discovery, a repository, dependency, candidate PR, or existing base is ambiguous.
3. Display the execution-plan preview required by the scheduling reference. Show the logical groups and their rationale when grouping applies, plus every root and discovered sub-issue, its group, hierarchy/source, triage disposition, request repository, implementation repository, base, entry phase, true implementation dependencies, execution wave/order, configured concurrency, selected execution driver, detected environment, compact membership evidence, capability outcome and relevant navigation information, and whether `DOMERGE` is enabled, the resolved `REVIEWER` value, the resolved review profile with how it was resolved plus that profile's preview additions, each target's estimated effort tier with the review and fix models and effort it implies (or the explicit `EFFORT` value), and which review phases are skipped. Then ask exactly for `go` or `no-go`. Stop after the question. Do not acquire a batch/target lock, create durable batch records, launch any agent, Herdr pane, tmux session or Screen session, create a worktree or branch, push, edit a PR, or start implementation before a separate user response explicitly says `go`. A `no-go` ends without execution. Instructions other than an explicit `go` amend the proposed plan; redisplay the complete revised plan and ask again.
4. After `go`, revalidate changing remote facts and execution capability. If the implementation repository, target set, base, dependency graph, entry phase, order, concurrency, execution driver, merge intent, reviewer setting, review profile, or effort override changed materially, display a revised complete plan and require a new `go`. Otherwise initialize the version 5 approved plan, including `review_profile`, its `review_profile_sha256` and `review_profile_snapshot` for a supplied file, and any `effort_override`, through `scripts/batch.js` under `<common-git-dir>/bork-doitall/<batch-id>` with the exact preview and approval hash. Persist per-host authenticated login, driver, environment_selection and capability record, required commit identity from applicable user/repository instructions (otherwise local Git author configuration), and task briefs. Store a discoverable active-batch pointer under `bork-doitall`. Keep records outside disposable worktrees. Do not initialize over an active batch; reconcile it on resume.
5. Use `scripts/tmux.js` action `schedule` for read-only preview planning only. For execution call `scripts/batch.js` action `reserve` to persist dependency blockers and atomically reserve launch IDs as `starting` before launching masters through the selected driver. Persist `max_concurrency` in the plan: default `1`, or the explicitly requested `2` or `3` (use `3` for an unqualified request to run in parallel). Launch only returned IDs and record each through `started`. The coordinator owns queue state; masters publish only their own phase/result records through the batch runtime.
6. Each master executes the target workflow and returns durable evidence. Poll phase and native-agent records with bounded foreground waits, reusing unchanged snapshots. Waiting for the selected reviewer still occupies a slot. A completion/block releases a slot only after that target's master and descendants stop. Preserve blocked descendants and continue independent targets. Apply [surfacing interactive attention](references/panes.md#surfacing-interactive-attention) on every poll: message the user immediately when a master or descendant needs an answer or approval.
7. For hc, accept the durable final turn and stop owned master processes through the [hc lifecycle](references/hc.md) before releasing a slot. Reconcile each stopped native master from its agent result and durable phase evidence, then call `target-complete` or `target-blocked` before releasing a slot. For Herdr, reconcile and close owned stopped master panes under its execution contract. For tmux, reap owned dead master panes during every poll: capture visible output and exit evidence, reconcile the durable outcome, then close the pane even for blocked or failed outcomes. Do not close a live master merely because its task is blocked or failed, and never delete unrelated hc, Herdr, tmux or Screen sessions/panes.
8. When no runnable/active implementation targets remain, run the approved `DOMERGE` finalization pass in [target workflow](references/target-workflow.md#batch-merge-finalization) before reporting. Without approved merge intent, finish after implementation. Summarize complete, blocked, and skipped targets with linked PRs, review and merge outcomes, validation and actionable blockers. Keep bases/parents, phase history, commits/pushes, selected-reviewer evidence, agent IDs, any fallback attach commands, and retained worktrees in the durable batch result. Do not claim completion while a target or merge finalization is still active. Keep dependency-blocked/ambiguous targets explicit.

## Final Output

When finishing, both the target master and batch coordinator must print exactly `Done` on its own line, followed by a blank line and a concise summarized report. Use plain text for `Done`, without a heading, punctuation, or decoration. Follow the shared [TLDR reporting contract](../bork-review/references/reporting.md): one concise row/bullet per target and at most one batch details link. Keep detailed evidence in durable result records. Clearly identify complete, blocked, and skipped outcomes. When a selected-reviewer approval exists, state whether it covers the final head; if commits landed after the approved commit, say the approval sits on the pre-fix commit. Report a goodcode loop-guard stop as blocked with its PR-too-big recommendation; `Done` means the run has ended, not that blocked or skipped work succeeded. Do not print it while work is still active.

## Resume

For runs started before the BORK rename, also inspect the pre-rename records and active-batch pointer under the recorded common Git directory. Reuse their recorded paths, locks, worktrees, branches, and agent or pane IDs; do not initialize a duplicate run under the new name or rewrite the approved preview merely to rename it.

Resume through the recorded driver and call `scripts/batch.js` action `inspect` before retrying any phase or mutation. Inspect native-agent IDs or hc, Herdr, tmux or Screen session/pane IDs, processes, phase records, worktrees, remote SHAs, ownership and PR draft states. Reconcile stopped or vanished masters and descendants from their original results and durable records; for hc, Herdr, tmux or Screen, capture exit evidence/output and close owned stopped panes under the recorded driver contract. Never count a vanished agent/pane or successful process exit as a successful skill run. An approved active batch resumes without another approval only when its stored plan, driver, merge intent, reviewer setting, review profile, effort override, and material remote facts remain unchanged; otherwise show the revised plan and require a new `go`. A legacy or incomplete batch without approval evidence must pass the gate before new mutations. Resume only the first incomplete phase after reconciling possible mutations. An implementation prerequisite releases its dependents only after its applicable goodcode, promotion and selected-reviewer gates, and cleanup succeed. Failed cleanup is a blocker, not a completed prerequisite. Keep successful and failed reports in durable records.

Screen masters use the [GNU Screen contract](references/screen.md), including exact session/window records, retained output, interruption and stopped-process cleanup. Apply the same phase gates and recovery rules as other terminal drivers.
