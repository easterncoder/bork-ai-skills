# hc Execution


For batches carrying a layout journal, [shared layout](../../bork-doitall/references/layout.md) supersedes the separate-session/sibling-pane placement instructions below. Use the recorded stable role slot. V2 creates only imminent workers and removes each accepted, stopped role pane; later passes recreate it with a new task identity. V1 retains its recorded fixed panes through turnover. Existing approved runs and standalone launches without a journal keep their original lifecycle contract. App/hc and Screen use the verified public tree/display adapters described in that contract; enforce their precise context, geometry and recovery gates.

Use `execution_driver: hc` for the separate herdr-core CLI, verified with hc 0.1.13. This is not the older Herdr TUI. Target masters retain native prify/goodcode children; goodcode's review/fix roles use the same hc lifecycle below. The shared [agent execution contract](panes.md) still owns scheduling, approval, roles and host capacity.

## Selection and identity

For new runs use verified membership priority **hc, Herdr, tmux, Screen, native**. Existing approvals keep their saved driver. Installation or an accessible shared core alone never establishes membership. Require inherited `HC_TERMINAL_ID`, the inherited `HC_SESSION` when set, a live `hc get <caller>` and `hc server status`. Verify the terminal PID is an ancestor of the caller (or the uniquely recovered frontend). The shared environment helper retains core ID, terminal ID, creation time, PID, session and manual capability evidence. Stale or partial explicit context blocks selection, including lower-priority contexts. Pass `expected_environment: "hc"` when membership is reported but hidden. Never copy IDs from an unrelated or focused terminal.

Read `hc --skill`, `hc --help`, `hc templates` and relevant command help before selecting it. `hcCapabilities` checks the installed manual and required lifecycle flags read-only. Independently verify the same host provider's interactive CLI, model controls, native nesting capacity and concurrent terminal capacity required by the role. Persist this capacity evidence in the ordinary environment selection. Background orchestration does not require `herdr-app`.

## Launch and delivery

After approval and batch reservation (masters only), prepare immutable job and launch JSON outside the worktree. The job uses the shared `argv` and unique `exit_record` schema, but hc launches the interactive provider directly instead of the exit-after-report terminal runner. Resolve templates to their actual executable/argv before creating the job, including their frontmatter command and initial instructions. **Every Codex command, including expanded templates, must include `--no-daemon`.** Never use provider print/exec mode. Put the initial task and exact skill/brief/result/acknowledgment paths in the provider's initial CLI message. Instruct the agent to report and remain available, and forbid additional agents except the master's explicitly scoped native children.

Invoke `node <skill>/scripts/hc.js launch <input.json>`. Input fields are `record` (new durable regular file path), `job`, `cwd`, unique `name`, `role` (`master`, `review`, `fix`), `run_id` and `task_id`, plus the verified caller `session` when context recovery supplied `HC_SESSION`. The adapter persists this routing identity and reuses it for later commands, including cleanup after the caller exits. The adapter uses `hc run --json --bg`, names and labels the terminal, records intent first and saves its returned address immediately, then retrieves creation identity. Workers stay hidden in headless mode. Visible layout is explicitly authorized by a requested shared layout, subject to its verified capability/geometry gate; do not create app spaces or tabs as a fallback. Record launch/terminal identity in the normal batch or per-role session before `started`.

Check `launch_reply.first_message.sent`. False or absent means delivery needs reconciliation, not success. Direct CLI tasks may have no first-message metadata. Read the exact terminal, wait for readiness, and require a durable acknowledgment matching `run_id`, `terminal_id`, `task_id` and the assigned brief. `acknowledge` accepts an `acknowledgment` regular-file path with those fields; the owner independently verifies its provenance and content. It proves receipt only, never completion. A trust or permission dialog goes to the user; never use `send --force` or keys to answer it automatically.

On an uncertain launch, use `reconcile` with `record`: it searches the recorded unique name, requires exactly one run-labeled terminal on the original core, and persists its address/creation time. Inspect command, cwd, parent, job and result before continuing. An absent/ambiguous match blocks automatic retry. Never overwrite launch intent, duplicate a live role, or replay uncertain mutations.

## Turns, attention and recovery

Use `inspect`, `wait`, `send`, `interrupt`, `acknowledge` and `cleanup` with the same `record` path. Wait uses `hc wait <id> --timeout 30`; a timeout or message is a check-in, not failure. Read output with `hc read <id> --lines 120`. Do not sleep or poll to wait for hc work. `inspect` returns `attention` for documented `status.state: blocked`, and structured navigation environment and argv. Render these for the user’s verified shell; default-session navigation also includes `hc attach <id>`. Immediately read and surface the exact permission/question prompt, target, role and terminal ID to the user and coordinator via the existing durable attention record. Never answer or force-send through it. Handle errors by reading and reconciling, never restarting the shared core.

Turn completion differs from process exit: the interactive worker may remain live and done/idle. Require the durable role result, matching fresh cycle/task acknowledgment, expected coordination state, reviewed HEAD and remote/cleanup gates. A message, OSC status, wait return or process exit never establishes success. Before cycle advancement verify no tools or native descendants remain active. A role-bound live interactive worker may receive another fresh brief through `send` (`task` and new `task_id`); persist send intent first. An uncertain send stays uncertain until readback and a matching acknowledgment prove receipt. Do not blindly resend. Provider sessions remain distinct from terminal IDs.

For recovery inspect the saved core, address, creation time, argv, cwd, labels, status, output, pending send and durable results before the first unfinished phase. Missing terminals, changed core/ownership, lost programs and `spawn_pending` require reconciliation. Never use `keep` to rerun a task: it recovers a shell only. If a provider cannot resume safely, accept or reconcile its previous turn, stop it and its descendants, then use a fresh immutable job/record for a replacement. Do not silently change drivers.

## Final cleanup and optional UI

Once all owned turns/results have been accepted and native descendants stopped, call `cleanup` with `results_verified: true` and `descendants_stopped: true`, backed by retained owner evidence. The adapter rechecks ownership, captures output, calls `hc kill <id>` if live, verifies `state: finished`, saves exit identity and calls `hc rm <id>`. This final shutdown replaces the other terminal drivers' exit-after-report convention. Do not remove the worktree or release a batch slot until shutdown, descendant and result evidence are reconciled. A cleanup failure retains its durable record for recovery. Never kill terminals without this run's exact identity and label, and never stop, update or restart the user's shared core/app.

Use `herdr-app` only for user-requested visible arrangement/navigation. First read `herdr-app --skill`, top-level help and the relevant discovered command help, then use explicit returned terminal/pane IDs. Installation does not authorize UI changes. Preserve all unrelated windows, tabs, spaces and terminals.

Live tests must distinguish synthetic OSC lifecycle probes from real provider behavior. Report untested trust prompts, provider task delivery/resume, descendant shutdown or crash recovery explicitly; offline fixtures and idle status are not live acceptance evidence.
