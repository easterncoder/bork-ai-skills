# Durable Batch Runtime

Use `node <skill>/scripts/batch.js <absolute-input-json>` for every version 5 `plan.json` transition after approval. The input is a JSON object with `plan_path`, `action`, and, except for `init` and `inspect`, the current `expected_revision`. The helper returns JSON with `ok`, `result`, and the new `state_revision`; an error returns `ok: false` and leaves the plan unchanged. Refresh the plan after a revision conflict. Do not edit runtime fields directly. The helper uses a batch mutex and atomic replacement. It performs no GitHub operation and trusts only explicit, freshly checked remote facts supplied by the caller.

`init` takes `plan` with `schema_version: 5`, the exact displayed plan in `approved_preview`, and `approval_evidence: {"response":"go","preview_sha256":"<SHA-256 of approved_preview>"}`. Initialize only after the separate explicit `go` and unchanged remote recheck. `init` also takes optional `review_profile`, `generic` (default) or an absolute readable regular profile file, with matching `review_profile_sha256` for a file; unknown names, missing files, and mismatched hashes are rejected. It also takes optional `effort_override`, `low`, `standard` or `high`; any other value is rejected. Keep the preview and hash in the durable plan. For new batches also supply `execution_driver` and the shared environment helper result as `environment_selection` (version 1). The runtime rejects unknown drivers, inconsistent membership precedence, missing active identity or unsuccessful selected capability evidence. This is additive schema 5 data; older approved plans lacking it remain readable and keep their driver. Transitions validate saved evidence without redetecting the coordinator environment. The caller verifies access to the recorded context on resume and blocks before new launches if inaccessible. An existing plan cannot be initialized again.

`init` validates every target's explicit `entry_phase` before saving the plan or reserving a master. In addition to the scheduler's common `status` and `depends_on` fields, supply the following nonempty strings. Missing, blank, or wrongly typed fields fail with the target ID, entry phase, and field name; unknown or absent phases are rejected.

| `entry_phase` | Required target fields at `init` | Head evidence |
| --- | --- | --- |
| `prify` | `issue_url`, `implementation_repository` | Prify publishes `pr_url` and `published_head` later. |
| `draft_goodcode` | `pr_url` | Draft goodcode publishes the validated head later. The legacy `draft` alias has the same inputs. |
| `ready` | `pr_url` | `published_head` is optional at initialization. The reviewer gate seeds it from the verified live ready PR; with reviewer `NONE`, target completion seeds it instead. |
| `finalize_merge` | `pr_url`, `published_head` | Preserve the completed implementation head and result evidence for the conditional merge pass. |

These checks validate launch inputs, not live GitHub identity or permission. The coordinator still records the repositories, checkout/remotes, records paths, instructions and base evidence described in [Queue Data](scheduling.md#queue-data). Existing saved plans resume under their original contract; this validation runs only on new `init` calls. Selecting `finalize_merge` does not bypass implementation completion or merge gates.

Persist the approved `reviewer` value, defaulting to `NONE`, and set `skip_ready_goodcode: true` exactly when it is `NONE` (including the `NOREVIEWER` alias). It may be combined with `merge_enabled: true` when both tokens and their effect were displayed and approved.

The coordinator calls `reserve` to atomically mark eligible targets `starting` and dependency failures `blocked`, then launches each returned ID. It calls `started` with `target_id` and `agent_id` after recording the master. It calls `inspect` on resume and before retrying a target. `reconcile_phase` means inspect the original child agent and result path; `reconcile_mutation` means inspect the recorded intent and GitHub state. Neither event authorizes another agent or mutation. After the master and descendants stop, call `target-complete` with its durable `result_path`, `master_stopped: true`, `descendants_stopped: true`, and `remote: {pr_url,head}`. The target result must have `status: complete`, `pr_url`, `published_head`, and `cleanup_success: true`. For a blocker, call `target-blocked` with stopped-agent flags, `reason`, and a regular JSON `evidence_path`. Then schedule again. A completed implementation prerequisite releases its dependents; a blocked one does not.

For `NOREVIEWER`, `target-complete` additionally requires freshly verified `remote.is_draft: false` and the target result's `ready_goodcode_status: skipped_noreviewer`. The helper requires draft goodcode and ready promotion when applicable, but no reviewer gate for `NONE`, and rejects `ready_goodcode` phase start. For an initially ready target with no phase or mutation records, supply `remote: {pr_url,head,state:"OPEN",is_draft:false}`. Completion seeds `published_head` only after the result matches that verified live PR/head and all completion checks pass.

The master calls `phase-start` **before** spawning prify, draft goodcode, or ready goodcode, using a new absolute `result_path` and `phase` (`prify`, `draft_goodcode`, `ready_goodcode`). Include `pr_url` and `expected_head` when known. The path is immutable for that phase. After the child and its descendants stop, call `phase-adopt` with `target_id`, `phase`, `agent_stopped: true`, `descendants_stopped: true`, and freshly checked `remote: {pr_url,head}`. Adoption reads the original child result. It requires `phase`, `status: complete`, `pr_url`, `published_head`, and `cleanup_success: true`; goodcode additionally requires `workers_stopped: true` and `reviewed_head` equal to `published_head`. A new master can adopt that result after the former master disappears. A pending or mismatched result remains pending and never justifies a duplicate child.

For ready promotion, the master calls `mutation-start` with `kind: ready`, `pr_url`, and `expected_head` only after the draft goodcode result is adopted and all promotion checks pass. The returned `perform_once` permits one `gh pr ready` attempt. On interruption, inspect GitHub and the saved intent. Never call ready again on that intent. Call `mutation-observe` with the exact PR/head and `is_draft: false` only after verifying this ready event belongs to the approved workflow. When `reviewer` is `NONE`, skip the external gate and ready goodcode. Otherwise request the selected reviewer as described in the target workflow. After qualifying selected-reviewer completion, write a regular JSON evidence record with `status: complete`, `pr_url`, `head`, and the exact `reviewer`; call `gate-complete` with its path and matching remote identity. Then start ready goodcode. For an initially ready target (`entry_phase: ready`) with no phase or mutation records, `gate-complete` seeds `published_head` from freshly verified `remote: {pr_url,head,state:"OPEN",is_draft:false}`. The reviewer evidence must match that live head and recorded PR before either the head or gate is saved. No head is required at initialization; completed earlier phases continue to supply their recorded head.

After all implementation targets stop, the coordinator handles approved `DOMERGE` in reverse dependency order. The finalization master completes the full merge gate, using the applicable phase evidence when `NOREVIEWER` is also approved, then calls `mutation-start` with `kind: merge`, `pr_url`, `expected_head`. Its `perform_once` permits one conditional merge attempt. Call `merge-running` when that master is actively finalizing. On interruption, reconcile the exact PR/head with GitHub; never issue the merge again on a pending intent. Call `mutation-observe` with `remote: {pr_url,head,merged:true,merge_commit_url}` only after confirming the merge at the intended head. A verified unmerged PR may use `merge-blocked` with `reason` and `remote: {pr_url,head,merged:false}`. The remote check must be fresh. `merge-blocked` without a started merge intent may record a failed preflight gate.

The runtime enforces ordering, record identity, stopped agents, and one intent per external mutation. The caller still verifies authenticated ownership, approval scope, review evidence, bot identity and timing, checks, mergeability, and that a remote state change belongs to the recorded attempt. Preserve those facts in the existing phase and result records. An ambiguous external outcome remains pending or blocked; do not turn it into another attempt.

New runs write the selected-reviewer gate to `phase_records.reviewer_gate`. The reader also accepts the legacy `phase_records.cspf` key so approved runs can resume without repeating a review request. New gate evidence must match `plan.reviewer`; the key does not select a reviewer. Existing approved plans without `reviewer` retain their original gate and skip settings on resume.

## Resuming a blocked target

Only the coordinator calls `target-resume` after explicit continuation within the existing approved scope. Supply `target_id`, recovered `agent_id`, current `expected_revision`, and a regular JSON `evidence_path`. Evidence requires `batch_id`, `target_id`, `approved_preview_sha256`, matching `prior_master_agent_id` and `recovered_master_agent_id`, the exact `user_instruction`, and true `user_continuation`, `scope_unchanged`, `prior_master_stopped`, `children_reconciled`. Verify the former owner stopped, reconcile original child IDs/results, and archive earlier reports before resuming; do not launch another child to replace a pending phase.

For a published PR, supply freshly checked `remote: {pr_url,head,state:"OPEN",is_draft:true}` both in the transition input and identically in the evidence. For a ready-entry PR, use `is_draft:false`; before any phase or mutation has been recorded, the fresh remote head is checked without replacing an initialization-time head. The caller also records verified author, base/head repositories and unchanged base/driver/reviewer/merge/effort scope in that evidence. The helper checks the recorded PR/head, dependencies, capacity and absence of pending external mutation. It appends the original blocker verbatim and ownership/evidence identity to `resume_history`, changes only status/master identity, and increments revision once. Approval, blocker, phase records, immutable result paths and mutation records are retained. Ordinary stopped-child, validation, remote and cleanup gates still govern phase adoption. A read-only `inspect` or a pending child result never authorizes resume by itself.
