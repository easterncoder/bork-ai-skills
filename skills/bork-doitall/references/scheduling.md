# Target Resolution, Ownership and Scheduling

## Normalize Once

- Numbers and `#numbers` resolve against the explicitly identified checkout project. GitHub issues and PRs share a number space; use the issue API's PR discriminator or explicit PR API evidence, not a guess. Preserve URL host/repository/type as the request repository. Report unrelated targets individually.
- Resolve the implementation repository separately. For an existing PR, it is the verified base repository. For an issue, use explicit user direction first, then explicit issue requirements or linked implementation relationships, supported by verified GitHub and local-remote evidence. The request and implementation repositories may differ. Do not infer an implementation repository from similar names, labels, filenames, or general product familiarity. Require a local checkout with verified remotes and suitable access before execution. If more than one repository remains plausible, show the candidates and ask; do not put an ambiguous target behind the execution gate.
- Fetch the authenticated account with `gh api --hostname <host> user` using the same credentials as subsequent API mutations. Record `login` per host. Local Git author names/emails are not ownership evidence. Recheck on resume and before ready promotion/publication; a changed account blocks the target until reconciled.
- For an issue, inspect paginated issue timeline/relationships for open implementation PRs. No open PR: queue prify. Exactly one: require its author login to equal the authenticated login, then reuse it. Multiple candidates: ask which one, without editing any. A PR authored by someone else blocks that target and its implementation dependents; sub-issues without that dependency remain eligible. Do not ignore a foreign PR and create a duplicate.
- For an explicit PR, apply the same author check. Require the PR to be open. A closed/merged PR is reported, not reopened or replaced. Re-read `isDraft`: draft enters draft-goodcode; ready enters the selected-reviewer request/gate, then ready goodcode, without prify or ready promotion; with `NONE`, both review phases are skipped.
- Deduplicate issue/PR inputs resolving to the same PR into one target and report all aliases. If an issue is listed separately from its linked PR, do not reserve two slots or run twice.
- For every supplied issue, recursively enumerate its GitHub sub-issues using paginated relationship data. Record each relationship and discovery source. Run the same issue/PR, repository, ownership, and implementation-PR triage for every descendant. If permissions or incomplete pagination prevent a complete traversal, mark that root unresolved and ask before execution rather than silently omitting descendants.
- For a supplied PR, traverse sub-issues only when GitHub evidence explicitly links the PR to the canonical issue it implements. Record that issue as a root alias; do not infer an issue from matching text or numbers.
- Include every open actionable descendant as a canonical work target. Keep closed, duplicate, already-completed, and tracking-only descendants in the plan with an evidenced skipped disposition. A parent issue with sub-issues remains a work target only when its own acceptance criteria require separate implementation; do not create an empty umbrella PR.
- A GitHub sub-issue relationship records scope and hierarchy, not an implementation dependency. Populate `depends_on` only from concrete implementation ordering evidence under the dependency rules below. Do not stack a sub-issue PR on its parent merely because GitHub shows the hierarchy.

After canonicalization and deduplication, a batch may contain any number of supplied root targets. Duplicate root aliases count once. Verified sub-issue descendants remain in the same approved batch. Never truncate the supplied roots or discovered sub-issue tree, or split them into unapproved automatic batches.

## Logical Groups Within One Run

After normalization and deduplication, use [bork-batch](../../bork-batch/SKILL.md) in embedded planning mode when more than one distinct canonical root remains. Reuse the discovered targets, hierarchy, dispositions, repository evidence, existing PRs, and dependency evidence; fetch only missing context needed to judge relationships. A single canonical root skips this step, regardless of descendant count.

Logical groups describe related work within the same execution batch. Include each canonical target exactly once, with its aliases and disposition, and retain all hierarchy links even when a descendant belongs in a different group. Show a short evidence-based rationale for each group and any dependencies across groups. Keep independent targets as singletons when appropriate. Group membership alone creates no implementation dependency, shared branch, combined PR, concurrency change, or requirement to wait for an entire group. Preserve the existing dependency scheduler and stable input-order tie breaking; continue eligible independent work when another group is blocked.

The coordinator performs grouping read-only before the existing approval gate, without launching a planning agent or creating another approval step. Present groups inside the one complete execution plan rather than producing separate commands or execution runs. Persist the group membership and rationale in the exact `approved_preview`, which the existing runtime retains; no new runtime schema is required. Resume from that approved grouping rather than regrouping an active run. Any regrouping must appear in a revised complete preview and receive a new `go`.

## Plan Preview and Approval Gate

Complete normalization and dependency discovery read-only before execution. Print one compact plan containing:

- The authenticated GitHub login, requested concurrency, selected execution driver, its detected membership evidence, capability outcome and relevant navigation information, and whether `DOMERGE` enabled merging, the resolved `REVIEWER` value, the resolved review profile and its resolution source, each target's estimated effort tier (made from the issue, its triage and the area touched when no PR exists yet, or from the actual diff for an existing PR) with the models and effort it implies or the explicit `EFFORT` value, and the resulting review skips.
- Logical groups and their rationale when multiple canonical roots remain, followed by one row per canonical root or discovered sub-issue with its group, stable execution number, hierarchy/source, triage disposition, issue/PR URL, request repository, implementation repository, intended base repository/branch, entry phase, and implementation dependencies.
- Ordered implementation waves. For serial work, show the exact target order. For parallel work, group targets that may start together and show dependent targets in later waves. For `DOMERGE`, also show the serial reverse dependency merge order and that merging a dependent PR can require a fresh ready-goodcode run on its prerequisite's changed head.
- Blocked, skipped, or unresolved targets and the decision needed; never describe them as scheduled work.

End with `Go or no-go?` and wait for a separate response. Only an unambiguous `go` approves the entire displayed plan, including its displayed merge intent. `No-go` ends without execution. Any other response is a plan amendment or question; resolve it, print the complete plan again, and repeat the gate. Approval does not cover targets, repositories, bases, dependencies, phases, order, concurrency, or merge intent omitted from the preview. Treat only a standalone, case-sensitive `DOMERGE` token in the invocation as merge intent; lowercase, mixed case, and substrings do not enable it. A later change in merge intent requires a revised plan and another `go`.

Resolve `REVIEWER=xxx` before previewing the plan. Accept any nonempty value without a reviewer allowlist; preserve its spelling. Omission defaults to `NONE`. Exact `REVIEWER=NONE` and standalone, case-sensitive `NOREVIEWER` both disable external review and ready goodcode. Conflicting options need clarification before approval. Persist `reviewer` and derive `skip_ready_goodcode` as `reviewer === 'NONE'`. Display both settings and their effects, including with `DOMERGE`. A later reviewer change requires a revised preview and another `go`.

Before approval, allow read-only repository/API/CLI inspection only. Do not acquire locks, create or update durable batch records, launch agents, Herdr panes or tmux, create worktrees or branches, edit files, commit, push, change PR state, or request reviews. After approval, refresh changing remote facts and driver capabilities. Any material plan change, including the driver, invalidates approval and requires a revised preview and another `go`. Persist the approved snapshot and approval evidence when initializing the batch so an unchanged active batch can resume without asking again.

## Implementation Dependency Graph

Read issue/PR requirements, explicit dependency links, closing relationships and existing PR base branches. Save concrete evidence for each edge. Do not infer a dependency solely from similar filenames or labels. For clear edges, schedule automatically. For ambiguity, ask while unrelated work proceeds.

Keep GitHub sub-issue hierarchy in separate fields from `depends_on`. A sub-issue may run before, after, or alongside its parent according to its actual implementation dependencies.

- A target with a verified implementation dependency waits until that prerequisite completes prify if needed, draft goodcode, ready promotion, selected-reviewer review and final ready goodcode as applicable. Under approved `NOREVIEWER`, the final ready goodcode step is skipped and the prerequisite becomes complete after its remaining gates and cleanup. Its starting point is the prerequisite's final verified published head. GitHub sub-issue ancestry alone never triggers this wait.
- New PRs stacked on a verified prerequisite target its PR branch, not the default branch. Pass a `base_override` containing repository, branch, SHA and prerequisite PR URL to prify before it creates a worktree. The branch must exist in a repository where GitHub can represent that PR base and the workflow can push its head; incompatible fork topology blocks the dependent target, rather than copying/merging branches automatically.
- Preserve an existing PR's base. Ask before proceeding if inferred dependencies require a conflicting base; do not silently retarget it.
- More than one independent prerequisite cannot be represented as a single base. Block and ask for a stacking order. If all dependencies already form one ancestor chain, target its nearest prerequisite. Never merge independent prerequisites automatically.
- Except for verified sub-issue descendants of supplied roots, do not automatically add an outside issue as a work target. An outside prerequisite is satisfied only by an existing PR with reliable completed-workflow evidence and a usable published branch, or an explicit user confirmation of its readiness. Read-only use of an external prerequisite's base does not authorize modifying it. Otherwise block the dependent target and report the missing prerequisite.
- Use the scheduler's `blocked` map to persist cycle members and dependents of blocked or skipped prerequisites as blocked, with the returned evidence. A failed, ownership-rejected, ambiguous, or otherwise blocked prerequisite blocks its dependents. Recompute after each terminal transition so transitive dependents are classified. Independent targets fill available slots.
- If a prerequisite changes or merges before its dependent target starts, reconcile the recorded head/base first. Do not automatically retarget an existing PR after a merge. Report a missing/changed prerequisite base instead of rewriting the stack.

## Queue Data

See [required target fields by entry phase](batch-runtime.md) for the launch inputs validated by `init` and when `published_head` is seeded.

`plan.json` has `schema_version: 5`, `batch_id`, `original_repo`, invoking host, `execution_driver`, host capability evidence, additive `environment_selection` from the shared environment helper for new batches, CLI profile for Herdr or tmux mode, `max_concurrency` (default `1`; explicit parallel requests may select `2` or `3`), `merge_enabled` (true only for approved `DOMERGE`; absent means false), `review_profile` (`generic` or an absolute supplied profile path with `review_profile_sha256` and retained `review_profile_snapshot`; absent in older plans, which resolve by the profile rules on resume), `effort_override` (`low`, `standard` or `high`; absent means goodcode computes the tier), supplied root IDs, `approved_preview` containing the exact displayed plan, `approval_evidence` with `response: go` and `preview_sha256`, `state_revision`, `targets` keyed by stable IDs, and source/instruction references. Each target stores `status`, `merge_status`, `depends_on` (canonical in-batch implementation dependency IDs), `root_ids`, `subissue_parent_ids`, discovery evidence, triage disposition, stable execution number/wave, input aliases, issue/PR URLs, request repository, implementation repository, local checkout/remotes evidence, `entry_phase`, ownership evidence, base override or preserved base, records path, master agent ID and child agent IDs, `phase_records`, `mutations`, plus terminal session/pane IDs for Herdr or tmux mode. Resolved outside prerequisites are evidence, not missing graph IDs. Reconcile existing schema 3 or 4 batches under their original approved plans and drivers; do not silently reinterpret their merge state, switch drivers or add merge targets.

For every new plan, store `reviewer` (default `NONE`) and `skip_ready_goodcode` (true exactly when reviewer is `NONE`). Existing approved plans without `reviewer` retain their original behavior on resume; changing them requires a revised preview and `go`. Keep the skipped ready phase explicit in the target result.

Statuses are `queued`, `starting`, `running`, `waiting_review`, `complete`, `blocked`, or `skipped`. The active statuses are `starting`, `running`, and `waiting_review`; together they count toward the configured `max_concurrency`, with a hard ceiling of three. Only `complete` satisfies implementation dependencies. In approved `DOMERGE` batches, `complete` means the applicable phases and cleanup succeeded; its separate `merge_status` moves through `pending`, `starting`, `running`, then `merged` or `blocked` during finalization. Without merge intent, use `skipped_not_requested`. A merge blocker never retroactively changes implementation completion. Masters publish `target-result.json` with evidence, but the coordinator marks terminal queue status after verifying the result and stopped AI processes. Stable input order breaks ties between equally eligible targets. A waiting review continues to occupy the serial slot. Preserve the saved concurrency on resume; older plans without it default to one. When lowering concurrency while multiple targets are already active, let those targets finish and launch nothing until capacity is available. Do not stop active work solely to reduce concurrency.

The read-only scheduler helper previews slots; the [batch runtime](batch-runtime.md) serializes version 5 reservations and all subsequent transitions under its lock. Target locks in prify/goodcode prevent duplicate work in separate batches sharing the Git repository. A failed launch must be reconciled before releasing its reservation. Preserve a started agent or fallback session on uncertainty instead of launching a duplicate. No background polling process is needed: the invoking coordinator keeps bounded foreground polling active until batch completion or a reported blocker.

New selection evidence uses version 1 independently of batch schema 5. The runtime checks its membership precedence, selected capability and driver identity. Existing approved schema 5 plans without it retain their recorded driver; do not redetect or silently migrate them. Schema 3/4 recovery and incomplete-approval gates remain unchanged. A moved coordinator must verify access to the saved terminal context, not substitute its new environment or a focused pane.
