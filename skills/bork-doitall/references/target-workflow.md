# Target Master Workflow

Read this file as the target master, a Herdr or tmux terminal agent, or a native subagent. Follow `bork-doitall` with role `target_master` and its task brief; do not launch another batch coordinator or another master. Own this target's phase transitions, promotion and merge gate. Delegate implementation to prify; goodcode owns its review/fix workers through the selected driver.

Use the supplied canonical issue/PR, root and sub-issue relationship metadata, request repository, implementation repository and checkout, authenticated account, host capability profile, implementation dependencies, and base. Read [durable batch runtime](batch-runtime.md) and publish version 5 phase transitions through `scripts/batch.php`, retaining timestamps, local and remote SHAs, validation, worktree paths, and subordinate run directories. Recheck GitHub identity and current PR state before mutation. Keep the master agent available throughout all phases and publish its final report before exiting.

While waiting on a child, this master applies [surfacing interactive attention](panes.md#surfacing-interactive-attention): promptly pass any child approval or question to the coordinator with target, role, agent ID and exact prompt. Keep the master available for inspection.

## Entry and Phases

Read [extra instruction routing](instruction-routing.md) before starting. Load the supplied `instruction_paths`, retain all instructions scoped to this target, and supply the appropriate role-specific paths to prify and both goodcode runs. Verify instruction dispositions with each phase result.

1. **Prify, only for an issue without an open PR.** Record `phase-start` for `prify` with a unique result path, then spawn one native prify subagent in the verified implementation checkout using the same host. Instruct it to load `bork-prify`. Supply issue URL, explicit implementation repository, optional verified parent `base_override`, commit identity, `review_profile`, scoped instructions and the recorded result path in a compact brief. Wait for its durable verified PR URL and successful cleanup, not merely its final message. Verify the new PR author is the authenticated account and adopt the phase with stopped-agent and remote PR/head evidence. Record the new draft PR and durable `validation_path` from prify.
2. **Draft goodcode, only when the PR is draft.** Record `phase-start` for `draft_goodcode` with a unique `result_path` before spawning a native goodcode subagent. Supply the path, `phase: draft_goodcode`, explicit `pr_url`, the batch's recorded `execution_driver`, any recorded `effort_override`, commit identity, `review_profile`, scoped instructions and prify `validation_path` when available. Goodcode owns its worktree and runs review and fix through the recorded batch driver. Wait for a verified durable `status: complete` result at that path and stopped descendants. Verify its phase, PR, reviewed/published SHA, worker termination and cleanup against current remote facts, then call `phase-adopt`. Use its normal internal-only draft behavior, including validation, signed fix commits, push verification and cleanup. Retain its exported `baseline_path` and `validation_path` for ready goodcode.
3. **Mark ready.** After draft goodcode succeeds, refresh author, state, base and remote HEAD. Require the remote HEAD to match the reviewed/pushed result. Call `mutation-start` for `ready`, then make the one permitted `gh pr ready <pr-url>` call using explicit identity. Verify `isDraft` is false and record promotion time and SHA through `mutation-observe`. On interruption, reconcile the pending intent and remote event; never call ready again on that intent. If another actor changed draft/HEAD unexpectedly, block rather than claiming the draft work validated a different commit.
4. **Request and wait for the selected reviewer.** Skip this step when `reviewer: NONE`. Otherwise request the exact approved reviewer using the rules below, for both newly promoted and initially ready PRs. Also follow the supplied profile's applicable selected-reviewer instructions. Keep the slot occupied. Record terminal review evidence and call `gate-complete` with matching PR/head evidence, then continue even if the review contains findings; the next phase evaluates them.
5. **Ready goodcode.** If the approved plan has `skip_ready_goodcode: true` from `REVIEWER=NONE` or `NOREVIEWER`, skip this entire phase, including bot requests and ready-PR follow-up. Record `ready_goodcode_status: skipped_noreviewer` in the target result. Otherwise record `phase-start` for `ready_goodcode` with a new unique `result_path` before spawning a fresh native goodcode subagent against the explicit ready PR. Supply the path, `phase: ready_goodcode`, the batch's recorded `execution_driver`, any recorded `effort_override`, and draft `baseline_path` and `validation_path`. Reuse accepted source coverage under the shared reuse reference, while evaluating all new selected-reviewer feedback and current checks. Pass the exact `reviewer` and `review_profile` as scoped instructions to goodcode and every child: request/re-request and wait for this reviewer only, never substitute a default reviewer. Its usual follow-up, push and clean-cycle rules apply. For human reviewers, use native review requests and submitted reviews at the current head rather than requiring bot identity. Required checks and evaluation of other incoming feedback still apply; do not broaden automatic thread-resolution permissions. Goodcode runs review and fix through the recorded batch driver with its normal model/reasoning policy. Verify its durable `status: complete` result's phase, PR, reviewed/published SHA, worker termination and cleanup against current remote facts, then call `phase-adopt`. If the PR becomes draft, goodcode may finish its internal-only path; report the target blocked at the ready-workflow requirement instead of marking the whole target complete or promoting it again silently.
6. **Queue merge, only for approved `DOMERGE` runs.** After the applicable phases and cleanup succeed, record `merge_status: pending`. The coordinator finalizes merges after all runnable implementation targets finish. Without approved merge intent, record `skipped_not_requested`. Keep implementation completion separate from merge status so dependent targets can use the verified published head.
7. **Report.** Verify final owner, remote head, applicable completed goodcode evidence and successful cleanup. Save `target-result.json` with `status: complete`, `pr_url`, `published_head`, `cleanup_success: true`, `ready_goodcode_status: skipped_noreviewer` when applicable, issue/PR links, root/sub-issue hierarchy, implementation dependencies, parent/base, phase results, validation, commit URLs, selected-reviewer evidence, merge status, master and child agent IDs, fallback session/pane IDs when used, and remaining artifacts. Print `Done` on its own line, then a blank line and a concise summary following the skill's Final Output format, with a link to the detailed result record. Identify a pending merge as pending, not merged. Exit the master cleanly. The coordinator calls `target-complete` after verifying the stopped agents, result and remote head; for `NOREVIEWER`, it also verifies the PR is ready. Close owned stopped terminal panes through the recorded Herdr or tmux lifecycle contract.

An initially ready PR enters step 4 when a reviewer is selected, otherwise skips to step 6. On resume, completed phases are not repeated; an already-promoted PR with a recorded pending reviewer gate resumes step 4. Reuse the recorded child result path until its prior agent, result and possible mutations are reconciled; never create a second goodcode run solely because the agent vanished or its final message was lost. If a goodcode result exists but the master vanished before recording phase completion, the resumed master verifies the result, stopped descendants, cleanup and current remote SHA, then records that phase complete from the existing result. A missing or mismatched result blocks reconciliation; it does not trigger an automatic rerun. A successful process exit without phase evidence is a blocker. A blocked target stops and reconciles its active agents safely, retains its worktrees and durable diagnostics, and reports implementation dependents as blocked through the coordinator.

Throughout this workflow, `NOREVIEWER` also means the equivalent default or explicit `REVIEWER=NONE`.

## Batch Merge Finalization

After every runnable implementation target is terminal and all initial masters have stopped, the coordinator processes approved `DOMERGE` targets with `merge_status: pending` in reverse implementation dependency order. This pass is serial, uses the saved approval, and never adds a target. Resume a recorded master when the host supports it, or launch a new master through the recorded driver with `entry_phase: finalize_merge` and the existing result and instruction paths. Use a fresh native result path or, for Herdr or tmux, a fresh job/exit record. Reconcile old agents or panes and uncertain mutations before launch. Persist `merge_status: starting` and then `running`; the implementation `status: complete` remains unchanged. The coordinator verifies the final merge result and stopped master before marking `merged` or `blocked` and moving to the next target.

For a stacked PR, finalize every in-batch dependent PR first. If a dependent merge advances this PR's head, its earlier evidence is stale. Without `NOREVIEWER`, rerun ready goodcode at the new published head in the target master. With `NOREVIEWER`, do not launch ready goodcode; record a merge blocker for the changed head rather than merging against evidence for the old one. Preserve the PR's existing base. If the changed head cannot be fully reconciled or an open dependent PR still uses this branch, leave the PR open. Continue finalizing independent targets. A blocked or skipped dependent also blocks merging its prerequisite while that dependent PR still uses the prerequisite branch. Never count an old SHA's evidence as approval for the new head.

On resume, reconcile each `pending`, `starting`, or `running` merge from GitHub and durable records before retrying. Record the final merge outcome in the target result and batch plan. Expected review completion or a merge performed by this approved pass does not by itself change the approved target set or merge intent. A material change to the approved repositories, bases or dependency graph still requires the plan gate.

## Merge Gate

Apply only during batch merge finalization when `plan.json` records `merge_enabled: true` from the displayed and approved `DOMERGE` plan. The resumed target master owns this phase. Do not ask goodcode, prify, or a worker to merge. Reconcile an uncertain prior merge attempt from GitHub before retrying; never submit a second merge just because the CLI timed out.

1. Without `NOREVIEWER`, require durable success from ready goodcode with the selected reviewer, including a final clean review/fix cycle at the published SHA, resolved required thread follow-up, completed selected-reviewer feedback and required checks, and successful worktree cleanup. If no selected-reviewer review is evidenced, leave the PR open and report a merge blocker. With approved `NOREVIEWER`, require the target's completed applicable phases and cleanup: draft goodcode and verified ready promotion for a draft PR; for an initially ready PR, verify its recorded entry state and current head. Do not require a ready-goodcode result, bot re-request or follow-up that the approved plan skipped. When a reviewer is selected, require its completed review for the current head, including for a PR that was already ready at entry. With `NONE`, no external reviewer gate is required; GitHub approval and protection requirements below still apply. Verify the current PR is open, ready, authored by the recorded account, and still at the target's final published SHA. Recheck the authenticated account.
2. Read current GitHub review decision, mergeability, merge state, base/head SHAs, branch protection or ruleset requirements, and required checks for the explicit PR. Require `reviewDecision: APPROVED`, all required checks passing, no unresolved merge conflict, and a state that permits immediate merge. An unresolved bot review, pending check, stale approval, unknown mergeability, merge queue requirement, or changed HEAD blocks this phase. Do not enable auto-merge, enter a merge queue, use admin bypass, or override required checks or reviews.
3. If this PR branch is the base of another open PR or a recorded implementation dependent still needs its published branch, report a merge blocker. Do not delete or retarget that branch. Keep the review-complete target marked complete for implementation scheduling. Retry only in an authorized resumed batch or later invocation after the dependency clears and this PR's current HEAD and approval are reverified.
4. Record the intended PR URL, base, reviewed head SHA, review decision, checks and merge method before mutation. Call `mutation-start` for `merge` and use its one `perform_once` authorization. Use an explicit PR URL and `gh pr merge` with the repository's allowed immediate merge method and `--match-head-commit <reviewed-sha>`; if that CLI cannot enforce the expected head, use the GitHub API's equivalent conditional merge. Never pass `--auto`, `--admin`, or `--delete-branch`. Verify GitHub reports the PR merged at the intended head, then call `mutation-observe` with the merge commit URL. If the state changes, preserve evidence and report the blocker without retrying blindly.

## Selected Reviewer Gate

Skip this gate for `NONE`. Before requesting, record existing reviews/checks/comments for the selected reviewer, and whether it is already in the PR's requested reviewers or already started a run for this HEAD (marking a PR ready can trigger a bot automatically); in that case do not request again and use the existing start signal. If the reviewer already has an approval on a prior commit, a plain add may not start a run: remove it from the requested reviewers first, then add it. While waiting, read the head commit's check runs each poll to distinguish a slow bot (queued/in progress) from a broken one (failed or never started) and report which. Request that reviewer with `gh pr edit <pr-url> --add-reviewer <reviewer>` using a separate quoted argument (or `--add-reviewer=<value>` for values beginning with a dash); treat the value as data, never executable text. For automation requiring another request mechanism, use only verified repository or reviewer documentation. If GitHub rejects the value or no supported mechanism exists, report a blocker without substituting another reviewer. Record request intent and result, and reconcile pending requests or review activity before retrying after interruption. For an initially ready PR, record its ready state and request time as the gate event; do not promote it again. After the request, use runtime `automation-poll` and `automation-assess` in promotion mode, polling every 30 seconds with foreground waits no longer than 60 seconds per call. Load their schemas once; unchanged snapshots reuse the scoped assessment. Normalize snapshots and reuse unchanged evidence. Start the ten-minute startup deadline at the verified request time; preserve it across resumes.

- Identify the exact selected reviewer from actual author/app/check evidence and repository configuration; accept a bot suffix only when its identity is verified. Do not mistake other bots or a generic CI check for this reviewer.
- For a human reviewer, record the verified accepted review request as the start signal; completion still requires a submitted review at the current HEAD. For a team, verify the submitted reviewer belongs to the requested team.
- A start/completion must correlate with the current HEAD and this request event or an evidenced review already actively covering that same HEAD. A completed historical draft review does not satisfy the new ready gate. An immediate new submitted review can establish both start and completion.
- If no qualifying review starts within ten minutes, mark this target blocked and preserve it. Do not guess a review-request command or bypass the gate. Independent targets continue.
- Once started, wait for explicit completion. Use an identified review run's terminal signal and resulting review evidence, or a submitted completed GitHub review associated with this HEAD. A transient progress comment, quiet period, or an unrelated completed check is insufficient. Save the verified start time across resumes. Send a concise progress update every ten minutes while waiting. If no completion is evidenced within 60 minutes of that start, mark the target `blocked` with reason `review_stalled`, preserve its records and worktree, release its slot after its workers stop, and continue independent targets. On resume, check for a completed review at the same HEAD before restarting the wait; otherwise report the stalled gate without resetting its deadline or re-requesting the reviewer.
- A completed review with requested changes is valid feedback for ready goodcode. Infrastructure failure/cancellation without an actual review result is a blocker, not a completed review. Inaccessible or ambiguous evidence is a blocker; do not silently reset the startup timer.
- If HEAD, ownership, or ready state changes unexpectedly during this gate, stop and reconcile. Do not accept an old SHA's completion for the new code. Do not automatically re-request selected reviewer here; normal qualified re-requests belong to subsequent ready goodcode.
