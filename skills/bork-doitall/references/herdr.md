# Herdr Execution


For batches carrying a layout journal, [shared layout](../../bork-doitall/references/layout.md) supersedes the separate-session/sibling-pane placement instructions below. Use the recorded role slot and retain its pane through target turnover. Existing approved runs and standalone launches without a journal keep their original lifecycle contract. App/hc and Screen use the verified public tree/display adapters described in that contract; enforce their precise context, geometry and recovery gates.

Use this contract for `execution_driver: herdr`. Herdr hosts target masters; the master's prify/goodcode remain native subagents, while goodcode uses this same terminal contract for its review/fix workers under [worker execution](../../bork-goodcode/references/execution.md). In worker mode, substitute the owning goodcode agent, worker role and worker result/acknowledgment for the coordinator, master and target result below; no batch `reserve` or `started` is performed by workers. The shared [agent execution contract](panes.md) owns driver priority, capacity and role boundaries.

## Availability

Verify the installed CLI with `herdr --version`, `herdr --help` and `herdr --skill`. This contract targets Herdr TUI's `herdr` CLI, verified against 0.9.5, not the separate native app's `hc` interface. Follow the installed guidance and inspect relevant local help rather than assuming compatibility from the executable name.

Require `HERDR_ENV=1` and inherited or verified recovered caller pane/session context before any session control or inspection. If all membership signals are absent and there is no reported Herdr context, record Herdr as inactive. When the user reports being inside Herdr, pass `expected_environment: "herdr"` to the shared environment helper and reconcile sandbox, environment-filter or detached-backend boundaries under [agent execution](panes.md); missing tool variables do not disprove the user's context. When recovery is recorded, route every Herdr command below through the shared context-aware wrapper from that contract. Any explicit incomplete or invalid context blocks selection; do not evaluate another driver as a fallback. Do not attach to or control the user's focused session from outside Herdr, forge context variables, start a server, upgrade Herdr or stop a server to satisfy detection. Inside Herdr, verify `herdr pane current --current` and `herdr pane process-info --current` read-only, including the invoking process or recovered frontend ancestry and resolved socket identity. Require a reachable compatible API with pane split/run/read/process-info/close support, plus the invoking host's usable CLI and the role-specific capacity from the shared execution contract. A missing method or inaccessible explicit session blocks selection before approval.

Persist the resolved session identity, caller pane ID, installed version/capability evidence and resolved `cli_profile`. Use inherited environment values through the current host's environment API, not POSIX-specific variable syntax. Keep the same local session for the batch; do not target SSH machines or another host. Do not persist credentials. An API failure during execution requires reconciliation, not a switch to tmux or a new pane.

## Launch

Before approval, discovery is read-only. After approval, reserve targets through the batch runtime before creating any pane. For each returned launch ID:

1. Prepare immutable job and launch JSON files as described in [agent execution](panes.md). Use `role: master` for a target master, or `review`/`fix` for a goodcode worker, and the same absolute `cwd`, `job`, `argv` and unique `exit_record` contract as tmux. Include the absolute master skill, compact brief and result path in the verified host CLI invocation. The CLI must exit after the master reports, using a mode verified from local help. Keep its terminal input available for normal permission prompts. Resolve `shell` and build the runner command with the read-only `command` action before creating a pane; quoting errors block this driver without a partial launch.
2. Save launch intent with the caller pane, target, job and result identity. Inspect `herdr pane layout --pane <caller-pane-id>`. Split right for a wide pane or down for a tall/narrow pane, avoiding unusable geometry. Create one sibling master pane with `herdr pane split --pane <caller-pane-id> --direction <right-or-down> --cwd <absolute-cwd> --no-focus`. Do not create another workspace or tab.
3. Read the new pane ID from `.result.pane.pane_id` and save it as `master_pane` **before** submitting work. Treat IDs as opaque. Save the driver's session identity with it. Reconcile an uncertain split from the original intent and live topology before retrying; never assume a failed response means no pane was created.
4. Verify that the created pane is at an available interactive shell prompt. Submit one shell command through `herdr pane run <master-pane-id> <runner-command>`. Set `shell` in the launch JSON to the actual destination shell (`posix`, `powershell` or `cmd`), verified from the pane and local configuration. Use the command prepared before pane creation from `php <skill>/scripts/tmux.php command <absolute-launch-json>` and submit its returned `result.command` as one literal argument. The shared builder handles shell quoting without depending on PHP's OS. Unsupported shells and cmd arguments containing quotes, percent signs or exclamation marks are rejected; use a verified supported shell or record the selected driver blocked before launch. Do not interpolate prompt text into shell commands or assume a POSIX shell on Windows. This reuses the terminal-neutral `run` action; it never calls tmux. The runner executes the job argument array with the pane's terminal streams and writes the unique exit record.
5. Save submission evidence and call batch `started` with the recorded master pane ID as `agent_id`. A successful `pane run` acknowledges queued input, not that the master started or succeeded. On timeout or error, inspect that exact pane, process, job and exit record before any retry. Never resubmit an uncertain command or overwrite its exit record.

Use a distinct immutable job and exit record for each reconciled attempt, including merge finalization. Reuse an existing live master instead of launching a duplicate. Resolve provider prompt/model/reasoning flags from that provider's installed help; Herdr does not authorize changing hosts or bypassing permissions.

## Lifecycle and Recovery

Poll the recorded master pane, native child records and durable phase/results with bounded waits. Use `herdr pane process-info --pane <master-pane-id>` and `herdr pane read <master-pane-id> --source recent-unwrapped --lines 120`. When the CLI is recognized as an agent, `herdr agent get <master-pane-id>` supplies additional lifecycle evidence. `idle`, `done`, `unknown`, a missing agent, or a quiet pane never proves process termination or target completion. The unique exit record is process evidence only, not a skill result.

At an approval/question prompt, notify the user immediately with the exact prompt, target and pane ID. If `herdr agent get <master-pane-id>` confirms a recognized agent, save `herdr agent focus <master-pane-id>` and, when supported by installed help, `herdr agent attach <master-pane-id>` for navigation within that session. Otherwise, inspect `herdr pane layout --pane <caller-pane-id>` and, only if the target is still the adjacent pane in the split direction, save `herdr pane focus --direction <right-or-down> --pane <caller-pane-id>`. Preserve focus during routine background inspection. Never answer an approval merely to unblock the batch.

If an owned master must stop, first stop its native descendants through the invoking host interface. After verifying the recorded pane still contains that master, use `herdr agent send-keys <master-pane-id> ctrl+c` for a recognized foreground agent, or `herdr pane send-keys <master-pane-id> ctrl+c` for the owned runner. Inspect output, process information and durable records afterward; an interrupt acknowledgment does not prove termination. Never interrupt an unrelated or replaced occupant.

Before releasing a slot, verify that the master CLI and descendants stopped, reconcile its immutable job/exit evidence, durable result and current remote facts, then call `target-complete` or `target-blocked`. Capture output and diagnostics before `herdr pane close <master-pane-id>`, and close only the pane created and recorded for this target. Do not close a live master solely because its target is blocked. If the pane disappeared without sufficient process/result evidence, retain the blocker and reconcile possible mutations; do not infer success or rerun the phase.

On resume, inspect the saved Herdr session/pane, job, exit record, descendants and durable results before continuing the first incomplete phase. Do not substitute a pane from the focused session when the recorded context is inaccessible. Preserve unrelated panes, tabs, workspaces and sessions, and never stop the Herdr server as cleanup.

## Verified interface evidence

The installed Herdr 0.9.5 `--skill`, command-group help and `api schema --json` establish caller variables, `pane.current`/`pane.process_info` response shapes (including `shell_pid`), and split/run/read/close operations. The schema's successful envelope has `id` and `result`, not an `ok` flag. Consult the installed schema on compatibility failures.

Official [CLI reference](https://herdr.dev/docs/cli-reference/) documents membership/socket variables and pane controls. [Agent automation](https://herdr.dev/docs/agent-automation/) distinguishes queued submission, readiness and lifecycle state from task completion. [Socket API](https://herdr.dev/docs/api/) documents process inspection and caller-scoped reads. These support the existing terminal runner topology: Herdr owns terminal panes, target masters retain native prify/goodcode children, and goodcode's review/fix workers occupy owned terminal panes. Herdr itself does not supply native delegation depth or enforce BORK result/approval gates.

When this integration cannot be exercised inside a real managed pane, report live launch, attention, interruption/resume and cleanup as untested. Fixture responses and a local installed binary do not prove live lifecycle success.
